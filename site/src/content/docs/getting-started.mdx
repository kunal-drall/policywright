Everything on this page runs today against
[the repository](https://github.com/kunal-drall/policywright) and — except for
the live `record` fetch — needs no network access.

## Prerequisites

- Node.js ≥ 22 (declared in
  [package.json `engines`](https://github.com/kunal-drall/policywright/blob/main/package.json))
- npm

## Install

```bash
git clone https://github.com/kunal-drall/policywright.git
cd policywright
npm ci
```

## Run the demo

```bash
npm run demo
```

The demo records the committed fixture, synthesizes the spec, emits the
artefacts to `out/` (`spec.json`, `context-rule.json`, `summary.txt`,
`FrequencyLimitPolicy.rs`, `simulation-report.md`), and runs the dry-run
scenarios — asserting each behaves as expected. It exits non-zero if any
scenario deviates, so it doubles as a smoke test
([src/demo.ts](https://github.com/kunal-drall/policywright/blob/main/src/demo.ts)).

The same artefacts are committed under
[examples/](https://github.com/kunal-drall/policywright/tree/main/examples) so
you can inspect them without running anything — including, under
[examples/live/](https://github.com/kunal-drall/policywright/tree/main/examples/live),
the recording and emitted `context-rule.json` for a **real testnet**
claim + swap sequence, alongside the raw transaction captures they were
decoded from.

The fixture's addresses and symbols are labelled synthetic assets — well-formed
but synthetic contract addresses carrying the symbols BLND, XLM, and USDC (see
the
[fixture's own note](https://github.com/kunal-drall/policywright/blob/main/fixtures/recorded-tx.json)) —
never presented as real USDC. The live-capture assets are the Blend/Soroswap
_testnet_ mints, pinned and source-cited in
[docs/FACTS.md](https://github.com/kunal-drall/policywright/blob/main/docs/FACTS.md).

## Synthesize and simulate directly

```bash
# Synthesize a spec from the fixture; print the summary, spec.json, and context-rule.json
npm run cli -- synth

# Synthesize from a saved recording instead of the fixture
npm run cli -- synth --input examples/live/recorded-claim-swap.json

# Run the dry-run scenarios against the fixture's spec
npm run cli -- simulate

# Override synthesis knobs (anything omitted keeps its default)
npm run cli -- synth --lifetime 604800 --cap-multiplier 1.25
npm run cli -- simulate --constrain-arguments
```

With `--constrain-arguments`, the unobserved-route scenario (a swap routed
through a token the recording never touched) is **denied** instead of flagged.
All flags and defaults are listed in the [CLI reference](/reference/cli/).

## Record a live flow

```bash
npm run record -- <txHash> [<txHash> ...] [--account <G...|C...>] \
  [--network testnet|mainnet|futurenet] [--rpc-url <url>]

# Or ingest a saved simulateTransaction exchange instead of fetching hashes
npm run record -- --from-simulation <file.json>
```

A multi-step flow (like the Blend claim followed by the Soroswap swap) is
several transaction hashes — Soroban allows one `InvokeHostFunction` per
transaction. Passing every hash merges them into **one** `RecordedTx`, ordered
by ledger close time. `record` decodes the `InvokeContract` calls and
CAP-67/SEP-41 token events, resolves each token's symbol/decimals from its SAC
metadata (with an explicit `resolved: false` fallback when that is not
possible), and prints the merged recording as JSON
([src/sources/rpc.ts](https://github.com/kunal-drall/policywright/blob/main/src/sources/rpc.ts)).

- `--account` names the subject the movements are attributed to. Without it,
  the first transaction's source account is assumed and a warning records the
  assumption — smart-account flows usually act through a `C...` address, not
  the envelope source.
- `--from-simulation` ingests a saved `simulateTransaction` exchange
  (`source: "simulation"`) — simulation discovers the authorization tree an
  unsigned envelope does not carry.
- `--network` defaults to `testnet`; `--rpc-url` overrides the endpoint,
  including a node you run yourself.
- Failures return a typed error — `BAD_INPUT` / `TX_NOT_FOUND` / `NETWORK` /
  `DECODE_FAILED` — instead of empty output.

The live fetch itself is not exercised by the demo or tests, but its decoders
and multi-hash merge logic run network-free in
[test/recorder.test.ts](https://github.com/kunal-drall/policywright/blob/main/test/recorder.test.ts)
against the committed raw captures of real testnet transactions.

## The generated Rust policy

The demo also writes `out/FrequencyLimitPolicy.rs`. Its source is
byte-identical (at the default config) to the compiled-and-tested crate at
[contracts/frequency-limit-policy](https://github.com/kunal-drall/policywright/tree/main/contracts/frequency-limit-policy),
and every generated file is stamped with this header
([src/rust-policy.ts](https://github.com/kunal-drall/policywright/blob/main/src/rust-policy.ts)):

```rust title="out/FrequencyLimitPolicy.rs (generated — header excerpt)"
// =============================================================================
//  ILLUSTRATIVE / UNAUDITED — NOT DEPLOY-READY
//
//  Generated contracts are illustrative and unaudited — not for production
//  deployment until the Audit Bank audit.
//
//  This file was generated by policywright as a *starting point* for a custom
//  OpenZeppelin Stellar smart-account policy. It compiles and its unit tests
//  run against the real OZ `Policy` trait (stellar-accounts v0.7.2), and
//  policywright deploys instances to TESTNET only. It has NOT been audited
//  and MUST NOT be deployed to mainnet or used to guard real value.
// =============================================================================
```
