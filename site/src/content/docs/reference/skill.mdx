[`.claude/skills/policywright-grant/`](https://github.com/kunal-drall/policywright/tree/main/.claude/skills/policywright-grant)

## How to load it

It needs the policywright MCP server registered as `policywright` — the
committed `.mcp.json` does that after `npm ci`
([registration](/reference/mcp-tools/#registration-stdio-exactly-as-verified))
— and Soroban RPC access for `record` and `verify`; it is testnet-only
(`compatibility` field below). Claude Code picks project skills up from
`.claude/skills/` at the repository root, so opening the repository in Claude
Code (`claude`) is all it takes; the 2.0.76 project-skill loader is verified
statically in
[FACTS §16](https://github.com/kunal-drall/policywright/blob/main/docs/FACTS.md#gate-16--d22-skill-packaging-as-verified-2026-09-02),
and the human demo is the interactive run.
The package carries the six spec fields only — `name`, `description`,
`license`, `compatibility`, `metadata`, `allowed-tools` — and its
`allowed-tools` pre-approve exactly the four `mcp__policywright__*` tools:

```yaml title=".claude/skills/policywright-grant/SKILL.md — frontmatter"
name: policywright-grant
description: Turn a Soroban transaction the user already performed into a reviewed least-privilege OpenZeppelin smart-account policy with the policywright MCP tools — record the hashes, synthesize the rule, ask the clarification questions (spend cap, lifetime, route constraint, signer and policy addresses), re-synthesize with the answers, dry-run it, and hand over the reviewable artifacts. Use when the user says "grant permission to do X from this transaction", pastes Stellar/Soroban transaction hashes to delegate a flow, or asks to limit what a key or agent may do on a smart account. Never installs, deploys, signs, or submits anything.
license: MIT
compatibility: Requires the policywright MCP server registered as "policywright" (the repository's .mcp.json after npm ci) and Soroban RPC access for record and verify. Testnet only.
metadata:
  project: policywright
  deliverable: D2.2
  server: policywright
allowed-tools: mcp__policywright__record mcp__policywright__synthesize mcp__policywright__simulate mcp__policywright__verify
```

The reference validator accepts it (run 2026-09-02, also in CI):

```text
$ npx --yes skills-ref@0.1.5 validate .claude/skills/policywright-grant
Valid skill: .claude/skills/policywright-grant
```

## What it does

Say "grant permission to claim my Blend yield and swap it to USDC, here are
the transactions" with the hashes and the account, and the skill:

1. **records** the flow (`record`) and restates every call and token flow
   from the tool result — never from memory;
2. **synthesizes with defaults** (`synthesize`) to have real numbers, and
   presents the rule in plain language: scope, caps, what is uncapped and
   why, frequency and lifetime, the argument constraint, every `DELTA` note
   and warning, and whether the artifact would install as-is;
3. **asks the clarification questions** — in one numbered message, with the
   numbers from the outputs — and waits;
4. **re-synthesizes** with the answers (cap multiplier and window, lifetime,
   route enforcement, the signer and the deployed policy addresses);
5. **dry-runs** (`simulate`) with the same recording and config and shows the
   permit/deny/flag table — a policy is "reviewed" only after that, with
   `deviations: 0`;
6. **hands over** the artifacts and the one human install command
   (testnet-only). It calls `verify` only after the human has installed, and
   only if asked.

## The clarification triggers

Written before the skill was authored
([references/clarifications.md](https://github.com/kunal-drall/policywright/blob/main/.claude/skills/policywright-grant/references/clarifications.md))
and asserted by the test suite. The skill asks; it never assumes:

| #   | Trigger                                                                         | What the answer changes                              |
| --- | ------------------------------------------------------------------------------- | ---------------------------------------------------- |
| T1  | **Ambiguous cap** — always, per asset that flowed out                           | `capMultiplier`, `spendWindowSecs`                    |
| T2  | **Ambiguous lifetime** — always                                                 | `lifetimeSecs`                                       |
| T3  | **Multi-asset outflows**                                                        | one synthesis or separate delegations                |
| T4  | **Argument constraint on/off** — a swap-path token set was derived              | `constrainArguments`                                 |
| T5  | **A warning, a `DELTA` note, or `installable.asIs: false`**                     | proceed, narrow, stop; `installTargets`              |
| T6  | **Assumed subject** — the recorder assumed the first transaction's source       | re-record with the account                           |

The real T1 question, with the numbers the tools produced for the recorded
claim→swap sequence
([docs/skill-demo-script.md](https://github.com/kunal-drall/policywright/blob/main/docs/skill-demo-script.md#1-clarification-triggers-written-before-the-skill-was-authored)):

> "The recording moved **2.1394095 BLND** out. The default cap is that amount
> plus 10 % headroom (**2.3533505 BLND per 24 h**). Do you want (a) exactly the
> observed amount, (b) the default headroom, or (c) a different ceiling and
> window — e.g. up to 10 BLND per week?"

That is the funded plan's own example — "this transferred 50 USDC — cap at 50,
or allow up to 100 over a week?" — with real numbers: cap at the observed
amount, or allow more over a window. Answer (a) maps to `capMultiplier: 1`,
(b) keeps `1.1`, and (c) becomes a longer `spendWindowSecs` plus a multiplier
the skill states. In the demo conversation the answer was "keep the 10 %
headroom but over a week, lifetime 7 days, deny other routes", and the
re-synthesized artifact was installable as-is.

## Guardrails

Written into the skill body verbatim and asserted by
[test/skill.test.ts](https://github.com/kunal-drall/policywright/blob/main/test/skill.test.ts):

- **never install, deploy, sign, or submit** — there is no such tool; "just
  install it" is answered with the human command and no tool call;
- **always dry-run before calling anything "reviewed"**, and require
  `deviations: 0`;
- **always show the unaudited banner** whenever generated code is shown or
  mentioned;
- **always surface every `warnings`, `notes` and `scopeNotes` entry** that
  changes what the policy permits or can enforce, before asking for a
  decision;
- **never invent a hash, address, amount, or window** — every value comes from
  a tool output or the user's message;
- **ask, do not assume**, on every trigger above;
- **testnet only** — if the user names mainnet, the skill stops and says the
  toolkit is testnet-only until the audit.

## Limits, stated plainly

The skill cannot express a cap in a different asset, a per-function cap, or
differing per-asset ceilings in one run (T3 says so and offers separate
delegations). Argument constraints it enforces are offline-only — the dry
run denies them; no on-chain policy does. It is testnet-only.
