The harness evaluates candidate calls against a synthesized policy set before
anything is installed and reports whether each would be **permitted, denied,
or flagged** — and why. It is Tranche 2 deliverable D2.3 — _"The harness
outputs a permit/deny/flag report for a generated policy including an
argument-constrained case (BLND→XLM denied when enabled); tests green."_ —
implemented in
[src/simulate.ts](https://github.com/kunal-drall/policywright/blob/main/src/simulate.ts)
and reachable from the CLI (`simulate`), the demo, and the MCP `simulate`
tool.

## The standard scenarios

`buildScenarios` derives them from any spec: the recorded flow replayed (must
permit), one deny per enforced check, and — when an argument constraint was
derived — the **real** observed swap re-routed through a probe token: the
network's native XLM Stellar Asset Contract, derived from the network
passphrase and never present in the recording (`--probe-token` overrides).
Checks run in a fixed order; the first failure decides:

| Scenario                                     | Check                             | Expected                                              |
| -------------------------------------------- | --------------------------------- | ----------------------------------------------------- |
| replay recorded flow                         | all                               | ✅ permit                                             |
| over the spend cap                           | spending-limit                    | ⛔ deny                                               |
| call to an unseen function                   | scope                             | ⛔ deny                                               |
| call after rule expiry                       | lifetime                          | ⛔ deny                                               |
| over the frequency limit                     | frequency-limit                   | ⛔ deny                                               |
| BLND→XLM swap (route through unobserved XLM) | argument-constraint               | ⚠️ flag (default) / ⛔ deny (`--constrain-arguments`) |

A **flag** means: every enforced check passed — the call would be permitted —
but an advisory argument constraint was violated; the report says so and how
to close the gap. There is no on-chain flag.

## Self-describing reports

Every report carries its provenance: the recording (network, source, hashes,
subject), the **generated policy set** it was evaluated against — each policy
annotated with how it is realised on-chain (composed stock binding, generated
contract, or offline-only) — the mode, a decision legend, an **Enforced by**
column that attributes each decision to the artifact realising the deciding
check, and a token legend. For the real recording the over-cap deny is
attributed to the composed `stock:spending_limit` on rule `pw:xfer:BLND`, and
the over-frequency deny to the generated `FrequencyLimitPolicy` on rules
`pw:claim` and `pw:swap` — the two artifacts of D2.4, side by side under
[examples/live/fresh/](https://github.com/kunal-drall/policywright/tree/main/examples/live/fresh)
([compose vs. generate](/concepts/compose-first/)).

## Why enforcement is off by default

An argument constraint is derived only from the routes the recording happened
to contain — for the real claim→swap sequence, a single swap. Enforcing it by
default would silently narrow the delegation to exactly that route — a token
set of two — and deny a legitimate future route without the user ever choosing
that. So the default is **advisory**: the
constraint is always derived and always reported, a violation is permitted and
**flagged** with the gap named, and `--constrain-arguments` (or
`config.constrainArguments` through the MCP tools) turns it into a **deny**.
The skill asks the user which they want before re-synthesizing
([the skill](/reference/skill/#the-clarification-triggers)).

## Argument-level scope, and its limits

Constraints come from an explicit rule table — one rule, `swap-path`: for any
call whose name contains `swap`, the first contract-address vector argument
(the Soroswap `path`) yields the **set** of token addresses observed. They are
derived on every run and recorded on the spec; enforcement is a config
decision, **off by default** — an opt-in tightening, never a silent widening.

Stated plainly: set semantics only (no ordering, hop count, or amounts);
`swap-path` is the only rule; the address check is a StrKey shape check;
and **enforcement lives in the offline harness only** — no stock
OpenZeppelin policy can express argument-value scoping, so the rule as
installed on the (testnet-only) smart account
([smart-account install](/reference/smart-account-install/)) would permit
BLND→XLM until an argument-checking policy exists. That policy
is not built and is not one of the approved Tranche 2 criteria; it is tracked
in
[docs/T2-NOTES.md § Function-level scope enforcement as a policy](https://github.com/kunal-drall/policywright/blob/main/docs/T2-NOTES.md#function-level-scope-enforcement-as-a-policy).
