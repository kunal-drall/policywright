Everything before this page produces files for review. This page is the
explicit, **human-initiated, testnet-only** step that puts them on an
OpenZeppelin smart account, and the read-only step that proves what is
installed matches what was emitted. Nothing that signs or submits here — the
account creation and the install — is reachable from the MCP server or the
skill, by design, not by omission; only the read-only `verify` is also an MCP
tool. It is Tranche 2 deliverable
D2.5 — _"A testnet smart account with an installed generated policy;
end-to-end demo recorded."_ — delivered on the labelled **fallback signing
path**; the repository page is
[docs/smart-account-install.md](https://github.com/kunal-drall/policywright/blob/main/docs/smart-account-install.md).
The install binds the generated `FrequencyLimitPolicy`:

## The flow

<Mermaid
  code={`flowchart TB
  rec["record: CLI or MCP tool"] --> gen["generate: synth --signer … --policy-address … → context-rule.json (schema v2)"]
  gen --> dry["simulate: install --dry-run — validate against the OZ install signature, simulate ×2 in enforcing mode, submit nothing"]
  dry --> sign["sign client-side: .env key acting as Delegated(G) — local-fallback (used); a wallet via SEP-43 — primary (not built)"]
  sign --> inst["install: add_context_rule ×3 on the OZ smart account — testnet only"]
  inst --> ver["verify: read rules and params back, diff against the artifact → PASS / FAIL (read-only; also the MCP verify tool)"]`}
/>

1. **Record** — the real claim→swap sequence
   ([examples/live/recorded-claim-swap-fresh.json](https://github.com/kunal-drall/policywright/blob/main/examples/live/recorded-claim-swap-fresh.json)),
   from the CLI or the MCP `record` tool ([Getting Started](/getting-started/)).
2. **Generate an installable artifact** —
   `synth --signer delegated:G… --policy-address custom:FrequencyLimitPolicy=C… --policy-address stock:spending_limit=C…`
   puts the deploy-time facts into `context-rule.json` (schema v2: real
   `Signer` shapes, deployed policy addresses, relative `lifetimeLedgers`).
   The committed artifact's flags are pinned in
   [examples/live/fresh/synth.args](https://github.com/kunal-drall/policywright/blob/main/examples/live/fresh/synth.args);
   CI re-emits and diffs it
   ([ci.yml](https://github.com/kunal-drall/policywright/blob/main/.github/workflows/ci.yml),
   step "Live side-by-side artifacts … match the committed copies"). The
   policy addresses are real testnet deployments: the generated
   [`FrequencyLimitPolicy`](https://stellar.expert/explorer/testnet/contract/CDSVPSTSKMJ2EEP4FOJ3NNIJZY5DKVA3VV5BM453AOYIWCLD4NMG2ZPP)
   and OpenZeppelin's stock
   [`spending_limit` wrapper](https://stellar.expert/explorer/testnet/contract/CCOQPGEYKZVNDRIUFMP6IQRDUONOURWWDJTXP22SJZ7NICJX7VGS4W4E).
   The account itself is OpenZeppelin's own example smart account, vendored
   verbatim from `stellar-contracts` v0.7.2 into
   [contracts/multisig-account](https://github.com/kunal-drall/policywright/tree/main/contracts/multisig-account)
   (the `stellar-accounts` crate is a library and ships no deployable
   account), built from source, deployed by
   [scripts/deploy-account.sh](https://github.com/kunal-drall/policywright/blob/main/scripts/deploy-account.sh)
   with the `.env` public key as its single `Delegated(G)` signer and no
   policies (the `Default` admin rule, id 0), hash-verified:
   [`CBQ6H7IL…QHDT`](https://stellar.expert/explorer/testnet/contract/CBQ6H7ILH54ADWTVS7FCK36W7FY2RJJOWR4VGLZG7D4PZUG5FSA7QHDT)
   ([account.json](https://github.com/kunal-drall/policywright/blob/main/examples/live/testnet/account.json)).
3. **Simulate** — `npm run cli -- install --artifact … --account … --dry-run`
   (or
   [scripts/install-testnet.sh](https://github.com/kunal-drall/policywright/blob/main/scripts/install-testnet.sh)
   `<artifact> --dry-run`, which sources `.env` into the environment). The artifact is consumed **unmodified**:
   every field is validated against the checks the real contracts perform and
   refused if it would not install as-is. One transaction per rule, each
   simulated twice — the second time in enforcing mode with both
   authorization entries — and nothing submitted.
4. **Sign and install** — the same command without `--dry-run`. The
   transaction is signed **client-side**, on the operator's machine, through a
   labelled signing surface (below); the secret is read from the environment
   only and appears nowhere in output or logs. **Testnet only**: the CLI
   refuses any other network.
5. **Verify** — `npm run cli -- verify --artifact … --account … [--install-log …]`
   reads the account's rules and each policy's stored parameters through
   simulated getters, diffs them against the artifact, and prints PASS/FAIL
   row by row. Read-only; nothing signed; no key needed. Also the MCP `verify`
   tool.

## Why simulation alone is not enough

Every `add_context_rule` calls `require_auth` on the account's own address, so
the transaction carries an authorization entry whose signature is the
`AuthPayload { signers, context_rule_ids: [0] }` selecting the admin rule.
OpenZeppelin binds the selected rule ids into the digest —
`sha256(signature_payload ‖ xdr(context_rule_ids))` — which stops
rule-selection downgrades. A `Delegated(G)` signer is then authenticated by
`G.require_auth_for_args((auth_digest,))` _inside_ `__check_auth`: an entry
for `G` over `account.__check_auth(auth_digest)` that **simulation never
returns**. The installer builds it, simulates again in enforcing mode with
both entries (a wrong payload fails here, before anything is signed), signs,
and submits. This path was **proven on testnet on 2026-09-02** — three rules,
two auth entries each — and again by the demo-script run the same day (rule
ids 4–6). Details and the digest test vector:
[docs/smart-account-install.md](https://github.com/kunal-drall/policywright/blob/main/docs/smart-account-install.md#how-an-install-transaction-authorizes-and-why-simulation-alone-is-not-enough),
[docs/FACTS.md §8](https://github.com/kunal-drall/policywright/blob/main/docs/FACTS.md#gate-8--openzeppelin-smart-account-the-account-side-v072-verified-2026-09-02)
and [§14](https://github.com/kunal-drall/policywright/blob/main/docs/FACTS.md#gate-14--d25-testnet-smart-account-install-verify-verified-2026-09-02).

## The signing hierarchy, labelled honestly

| Mode                                         | What signs                                                                                                                     | Status                                                                                                                                                                                   |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Primary — wallet (`Delegated(G)`)**        | The wallet's `G` is the rule signer and the transaction source; it signs **the same transaction** via SEP-43 `signTransaction`. | **Not built** — the wallets-kit + Freighter page is the open cohort-wallet track; it replaces only the installer's `SigningSurface`.                                                       |
| **Fallback — local `.env` key**              | `Keypair.fromSecret(STELLAR_SECRET_KEY)` acts as `G`.                                                                          | **Used for every install so far**, labelled `local-fallback` in every output and log, with the reason: no SEP-43 wallet can sign an OpenZeppelin `External` digest, and the page is unbuilt. |
| Never                                        | MCP-driven signing or submission.                                                                                              | Structural rule; the server has no install/deploy tool ([MCP server](/reference/mcp-tools/)).                                                                                           |

## The one interactive human step

The install itself is the one human step: the operator runs the command,
and the client-side signing happens on their machine with their key. In the
fallback mode used so far there is no interactive approval prompt — the
`.env` key signs. In the primary mode, not built, the human would approve the
same transaction in Freighter. The end-to-end demo recording (the criterion's
second clause) is scripted beat by beat with real outputs in
[docs/demo-script-t2.md](https://github.com/kunal-drall/policywright/blob/main/docs/demo-script-t2.md);
it is the open item listed in
[evidence/EVIDENCE.md § D2.5](https://github.com/kunal-drall/policywright/blob/main/evidence/EVIDENCE.md#d25--testnet-smart-account-with-the-installed-generated-policy-fallback-path),
together with the Freighter setup for the primary mode. The optional
post-install enforcement demo (an in-scope swap through the account
succeeding, an over-cap transfer rejected on-chain) is not attempted. CI run
for this deliverable:
[33622880981](https://github.com/kunal-drall/policywright/actions/runs/33622880981).
