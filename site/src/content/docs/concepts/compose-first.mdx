Policywright's design rule: **the synthesizer configures stock OpenZeppelin
policies before ever generating fresh Rust.** New policy code is generated only
where no stock policy can express the constraint. This is the permanent
default, not a v0 shortcut. The stock building block v0 configures today is
`spending_limit`; the stock threshold policies — `simple_threshold` and
`weighted_threshold` — are the planned composition targets for multi-signer
flows (see [Planned](#planned)).

## Why compose-first is the default permanently

Generated authorization code guards user funds, and every freshly generated
line is a line nobody has reviewed yet:

- **Stock policies carry their review with them.** OpenZeppelin's building
  blocks are shared, maintained code. Configuring them means the enforcement
  logic executing on-chain is the same code everyone else runs and scrutinises
  — only the parameters are new, and parameters are auditable at a glance.
- **Fresh codegen multiplies audit surface.** A generator that emits a new
  contract per delegation produces code no audit has covered. Keeping
  generation as the rare fallback keeps the unaudited surface small and
  reviewable.
- **Parameters are legible to reviewers and wallets.** "Stock `spending_limit`,
  cap 1357.95 BLND per 24 h" is a statement a wallet, an agent, or a human can
  check mechanically. Arbitrary generated code is not.

For those reasons the ordering is not a maturity phase to grow out of: even
with a hardened generator, composing stock policies stays the first choice, and
generation stays the fallback.

## What v0 does today

- **Composes the stock `spending_limit` under its real install shape.** The
  emitted `context-rule.json` attaches `stock:spending_limit` with the
  parameters the real module takes — `{ spending_limit: i128, period_ledgers:
  u32 }`, seconds converted to ledgers — on a token rule the subject actually
  authorized a `transfer` on. Every binding carries its OZ `file:line` source
  citation
  ([docs/context-rule-schema.md](https://github.com/kunal-drall/policywright/blob/main/docs/context-rule-schema.md);
  a real binding is committed in the
  [live example](https://github.com/kunal-drall/policywright/blob/main/examples/live/context-rule.json)).
- **Records what stock policies cannot express as explicit delta notes —
  never as a shape the real contract would reject.** The stock
  `spending_limit` only meters direct `transfer` calls, verified against OZ
  source ([docs/FACTS.md §2.4](https://github.com/kunal-drall/policywright/blob/main/docs/FACTS.md)),
  so a cap on an asset the subject never directly transferred (the fixture's
  BLND, which moves inside the pool and router) becomes a named
  composition-delta note in `context-rule.json`, enforced meanwhile by the
  offline dry run.
- **Generates fresh Rust only where no stock policy exists.** OpenZeppelin
  ships no call-frequency policy, so the frequency limit is the one generated
  contract — implementing the real OZ `Policy` trait, byte-identical at the
  default config to the compiled-and-tested crate at
  [contracts/frequency-limit-policy](https://github.com/kunal-drall/policywright/tree/main/contracts/frequency-limit-policy),
  stamped `ILLUSTRATIVE / UNAUDITED — NOT DEPLOY-READY` on every emitted file
  ([src/rust-policy.ts](https://github.com/kunal-drall/policywright/blob/main/src/rust-policy.ts)).

## Planned

Composition of the stock threshold policies — `simple_threshold` and
`weighted_threshold` — is planned for when multi-signer flows enter the
synthesizer's scope; v0's worked example is a single-signer flow and does not
exercise them. See the [Roadmap](/roadmap/).
