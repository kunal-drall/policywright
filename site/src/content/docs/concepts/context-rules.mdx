In OpenZeppelin's
[Stellar smart-account model](https://docs.openzeppelin.com/stellar-contracts/accounts/smart-account),
a **context rule** binds an authorization to a scope and a lifetime; **policies**
attached to the rule then enforce programmable constraints. Policywright's
output mirrors that model: the synthesized `SmartAccountSpec` is a context rule
plus a minimal policy set
([src/types.ts](https://github.com/kunal-drall/policywright/blob/main/src/types.ts)).

## What v0 derives

From a recorded flow, the synthesizer
([src/synthesizer.ts](https://github.com/kunal-drall/policywright/blob/main/src/synthesizer.ts))
builds a context rule with:

- **Scope** — the distinct `(contract, function)` pairs observed, in first-seen
  order, deduplicated. Nothing that was not observed is ever added: a recording
  that called `claim` and `swap_exact_tokens_for_tokens` authorises those two
  pairs and no third
  ([scope-binding tests](https://github.com/kunal-drall/policywright/blob/main/test/synthesizer.test.ts)).
- **Name** — a short deterministic rule name derived from the called function
  verbs (e.g. `pw:claim+swap`), truncated to 20 **bytes** (multibyte symbols
  count per byte) because OpenZeppelin caps rule names at that length
  ([docs/FACTS.md §2.3](https://github.com/kunal-drall/policywright/blob/main/docs/FACTS.md#23-limits)).
- **Lifetime** — `validUntil` is a lifetime base plus the configured lifetime
  (`--lifetime`, default 30 days = 2 592 000 s). The base is an explicit `now`
  argument to `synthesize()`: the CLI, the demo and the MCP tools pass the
  recording's timestamp by default, so the result is deterministic and
  testable ([src/cli.ts](https://github.com/kunal-drall/policywright/blob/main/src/cli.ts),
  [MCP `synthesize.now`](/reference/mcp-tools/#synthesize)).

## Example

From the committed example run
([examples/spec.json](https://github.com/kunal-drall/policywright/blob/main/examples/spec.json)):

```json title="examples/spec.json — contextRule"
{
  "contextRule": {
    "name": "pw:claim+swap",
    "scopedCalls": [
      {
        "contract": "CCFZSK3W5W54JT2QPLBDDQ5W4JEIVBG3PUFONKE5YOMS52L6GQIPIV4V",
        "fnName": "claim"
      },
      {
        "contract": "CBGAPUV74GVQYQYBHMIN4LF5ZEHYIMM4L5VBGUBB4IJXM5D4RQ7275J7",
        "fnName": "swap_exact_tokens_for_tokens"
      }
    ],
    "validUntil": 1751414400
  }
}
```

The dry-run simulator enforces the rule in the same order the checks are
documented: a call outside the scoped pairs is denied with reason `scope`; a
call after `validUntil` is denied with reason `lifetime`
([src/simulate.ts](https://github.com/kunal-drall/policywright/blob/main/src/simulate.ts)).

## From spec to installable rules

The spec above is the offline, function-level view. The emitter also produces
`context-rule.json`: the same authorization expressed in the shape
OpenZeppelin's `add_context_rule` actually takes, verified against the pinned
`stellar-accounts` v0.7.2 source
([docs/context-rule-schema.md](https://github.com/kunal-drall/policywright/blob/main/docs/context-rule-schema.md)).
The mapping is honest about what the on-chain model can and cannot carry:

- **One `CallContract` rule per contract — plus one per token the subject
  authorized a direct `transfer` on.** An OZ context rule binds exactly one
  contract, and `__check_auth` receives one context per `require_auth`, so the
  claim+swap flow emits `pw:claim` and `pw:swap` for the two contracts called
  and, from the real recording's authorization tree, `pw:xfer:BLND` for the
  BLND token whose `transfer` the account authorized inside the swap — the rule
  the stock `spending_limit` composes on
  ([examples/live/fresh/context-rule.json](https://github.com/kunal-drall/policywright/blob/main/examples/live/fresh/context-rule.json);
  [compose vs. generate](/concepts/compose-first/)). The `Default` rule type is
  never emitted — it would authorize everything
  ([test/oz-context-rules.test.ts](https://github.com/kunal-drall/policywright/blob/main/test/oz-context-rules.test.ts)).
- **On-chain matching is contract-level.** OZ context rules cannot carry
  function names. The observed functions are included as advisory
  `observedFns`, function-level narrowing stays the offline dry run's job, and
  the gap is recorded as a composition-delta note.
- **`valid_until` is a ledger sequence on-chain,** not a Unix time. The
  configured lifetime is converted at OZ's own estimated 5 s/ledger basis into
  a relative `lifetimeLedgers` (schema v2); the installer adds it to the live
  ledger head at install time — the only `add_context_rule` argument it
  computes ([src/install.ts](https://github.com/kunal-drall/policywright/blob/main/src/install.ts)
  `planInstall`; the authorization entry's nonce, expiration ledger and digest
  are computed too and recorded in the install log) — and the conversion is
  recorded in a note.
- **Signers and policy addresses are deploy-time facts.** `synth --signer` and
  `--policy-address` put them into the artifact in the real OZ `Signer` shape
  and as deployed contract addresses; without them the artifact is a design
  document and the install gate refuses it (`add_context_rule` requires at
  least one signer or policy per rule, and the stock `spending_limit` needs an
  authenticated signer). The MCP `synthesize` tool reports the same verdict as
  `installable.asIs` — see [smart-account install](/reference/smart-account-install/).

Read the `notes` array before installing: it lists every unit conversion,
every constraint the stock policies cannot express, and every install-time
obligation. Installing is a separate, explicit, human-initiated CLI step and
is **testnet-only** — the `install` command refuses any other network
([smart-account install](/reference/smart-account-install/)).
