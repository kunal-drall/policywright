Policies are the enforcement half of the synthesized output: quantitative
constraints bound to the [context rules](/concepts/context-rules/). v0
synthesizes three policy kinds in the offline spec, defined in
[src/types.ts](https://github.com/kunal-drall/policywright/blob/main/src/types.ts)
and derived in
[src/synthesizer.ts](https://github.com/kunal-drall/policywright/blob/main/src/synthesizer.ts) —
and then maps them onto **real OpenZeppelin install shapes** in
`context-rule.json`
([schema](https://github.com/kunal-drall/policywright/blob/main/docs/context-rule-schema.md)).

## `spending-limit`

In the offline spec: a **gross-outflow** cap per asset over a rolling window —
`observed gross outflow × capMultiplier`, rounded up, with the observed amount
carried for transparency. One policy per asset that left the account; assets
that only flowed in get no policy at all (see the
[least-privilege model](/concepts/least-privilege/)). The dry-run simulator
enforces this cap over any outflow of the asset.

```json title="examples/spec.json — the BLND spending limit"
{
  "kind": "spending-limit",
  "asset": {
    "contractId": "CBG4EBVOIT77IWCNJOL4BVAAOIVAH7W7YSLK5UI4N6SGNFSHGSEXMA2W",
    "symbol": "BLND",
    "decimals": 7,
    "resolved": true
  },
  "cap": "13579500000",
  "windowSecs": 86400,
  "observedGrossOut": "12345000000"
}
```

In the installable `context-rule.json`, the cap becomes OpenZeppelin's **stock
`spending_limit`** — with its real install params,
`{ spending_limit: i128, period_ledgers: u32 }` — wherever the recording
supports it. The stock policy's verified semantics
([docs/FACTS.md §2.4](https://github.com/kunal-drall/policywright/blob/main/docs/FACTS.md))
constrain where that is:

- Its `enforce` only meters **direct `transfer` calls** (reading the amount
  from the third argument); any other function — including a router swap —
  panics `NotAllowed`.
- Its window is measured in **ledgers**, not seconds; Policywright converts
  (at OZ's own 5 s/ledger basis) and records the conversion in a note.

So the binding attaches on a token rule the subject actually authorized a
`transfer` on (the committed
[live example](https://github.com/kunal-drall/policywright/blob/main/examples/live/context-rule.json)
carries one: `stock:spending_limit` on the native-token rule). When the
recording shows no subject-authorized direct transfer of a capped asset — as
in the offline fixture, where the BLND moves inside the pool and router — the
cap is recorded as an explicit **composition-delta note** rather than emitted
in a shape the real contract would reject. See
[compose-first](/concepts/compose-first/).

## `frequency-limit`

Bounds how often the scoped calls may run within a rolling window (default: at
most 5 calls per 24 hours, both configurable). One frequency-limit policy is
always emitted. OpenZeppelin ships **no stock policy for call frequency**
([docs/FACTS.md §2.4](https://github.com/kunal-drall/policywright/blob/main/docs/FACTS.md)),
so this is the one policy rendered as generated Rust — implementing the real
OZ `Policy` trait, byte-identical at the default config to the
compiled-and-tested crate at
[contracts/frequency-limit-policy](https://github.com/kunal-drall/policywright/tree/main/contracts/frequency-limit-policy)
(25 Rust tests; a hash-verified instance is deployed on testnet — see
[Security](/security/)).

## `argument-constraint`

Constrains a positional argument of a specific call to an observed allow-set.
Constraints come from an explicit derivation-rule table; the one rule today is
`swap-path`: for any call whose name contains `swap`, the first
contract-address vector argument (the Soroswap `path`) yields the **set** of
token addresses the observed route touched. The observation is **always**
recorded on the spec (as `argumentScopes`, tagged with its rule); whether it is
enforced depends on config:

- **`--constrain-arguments` off (default)** — advisory. A candidate swap
  routing through an unobserved token is **flagged**: permitted by every
  enforced check, with the scope gap named in the report.
- **`--constrain-arguments` on** — enforced. The same candidate is **denied**,
  and the reason names the rule, the call, the argument, the allow-set, and
  the offending token.

Proven both ways on the real recorded claim→swap sequence: BLND→XLM (XLM being
the network's native asset contract, never observed) is flagged by default and
denied when enabled —
[committed reports](https://github.com/kunal-drall/policywright/tree/main/examples/live).

It constrains the token _set_, not the ordering, hop count, or amounts — amount
bounds are the spending limit's job
([README: argument-level scope](https://github.com/kunal-drall/policywright#argument-level-scope---constrain-arguments)).
This enforcement exists in the **offline dry run only**: no stock OZ policy can
express argument-value scoping, so `context-rule.json` records it as a delta
note. On-chain enforcement would need a generated policy whose `enforce` reads
the argument; that policy is **not built** — it is tracked as open design work
in
[docs/T2-NOTES.md](https://github.com/kunal-drall/policywright/blob/main/docs/T2-NOTES.md)
and is not one of the approved Tranche 2 criteria (see the
[Roadmap](/roadmap/)).

## The five-policy budget

OpenZeppelin smart accounts allow at most **5 policies per context rule**
(`MAX_POLICIES` in
[src/types.ts](https://github.com/kunal-drall/policywright/blob/main/src/types.ts)).
When a synthesized spec exceeds that — for example, a recording with six
distinct outflow assets — the synthesizer emits a warning on the spec rather
than failing, and suggests splitting the flow across multiple rules
([test: warns when the policy count exceeds the OZ max](https://github.com/kunal-drall/policywright/blob/main/test/synthesizer.test.ts)).
